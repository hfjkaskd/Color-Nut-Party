# 钻石奖励算法对照采样报告（2026-09-10）

已将原先“按关卡轮播有限样本”的实现替换成可配置的余额随机区间模型。它是黑盒行为模型，不是拿到了原版服务器源码，不应宣传为完整算法已被证明一致。

## 本次证据与验证

累计保存 242 笔成功结算预览响应：巴西 100 笔，印尼 142 笔；其中 230 笔为非零钻石。每国两个既有测试账号。所有采样仅调用游戏结算预览，不调用提现或伪造广告完成；预览本身会推进这些测试账号的服务器关卡计数。

- 固定余额跨关卡重复：BR 33000 与 ID 9300000 各新增 12 次。奖励变化，排除固定样本轮播。未证明所有随机分布。
- 第二用户：两国前 3 次均为空，第 4 次非零。不同金币余额与发送关卡数下，钻石仍在相近区间。
- 先冻结 v3 再采 30 个新余额点：29/30 覆盖。反例为 ID 9250000 返回 2319，高于估计上限 2200。
- 将该档估计范围改为 1000–2500，冻结 v4，再对两个用户采 8 笔新响应：8/8 覆盖。
- v4 对全部非零记录回查 230/230 覆盖，这包括训练数据，不能等同于独立验证通过率。

原始条件、完整脱敏响应、冻结版本和失败记录在 `RewardEvidence/DiamondAlgorithm/`。`validation-report.json` 可逐条核对，没有将超出预测范围的响应删掉。

## 模型

完成关卡数小于 4：钻石为零。之后按奖励国家和当前钻石余额选档，在该档 minimum–maximum 内均匀抽样，BR 保留两位小数，ID 取整。区间下界包含在新档；高于最后余额边界使用末档。ID/IDN 使用印尼，其他奖励国家默认巴西；实际显示国家、货币、提现渠道仍走原来的显示配置。

巴西候选基数 × 0.8–1.2 可以覆盖已采记录；印尼的统一倍率假设有反例，因此改用独立上下限。印尼上下限由采样值向外取整估计，不是原版下发配置。均匀分布、精确边界及 MidpointRounding.AwayFromZero 都是当前本地模型选择：区间覆盖不能证明这些细节与服务器一致。

## 工程行为

`LocalDiamondRewardPolicy` 是纯数值规则；静态参数在 Resources/Configuration/LocalDiamondSettlement.json，不动态搭建 UI。结算首次计算后写入 LocalPendingReward，重进不重新抽样。已领取记录不会重复入账，既有待领取奖励保持原值；旧截图临时值或等待服务标记可由新模型补齐。现金和钻石同次保存，顶部余额刷新。所有运行平台走相同代码。

保留 ApplyOriginalDiamonds 用于接收指定关卡的成功响应，不代表生产游戏已直连原版服务器。本文只覆盖结算预览钻石；没有将广告按钮的 10X 自动推定为钻石乘十，也没有伪造广告领取或真实提现。

## 尚未证实

缺少服务器代码、实际 RNG 状态及完整用户分流配置，无法仅凭这些响应唯一确定完整算法。未验证所有国家、真实广告归因分组、所有游戏版本或将来的服务端改动。新独立数据仍可能否定当前区间；届时应记录反例并复测，而不是事后修改旧验证结果。

## Unity 验证

OriginalDiamondInputValidation 覆盖两国所有配置档的端点与前一单位、随机上下端值、BR 默认规则、前三次零奖励、待领取保持、非法数据拒绝和重复领取。LocalCashRewardPlayValidation 覆盖真实棋盘最后一步、双奖励显示、广告回调防重、重载和两种余额持久化。

本轮最终验证通过：NUT_ORIGINAL_DIAMOND_INPUT_PASS（diamond-algorithm-v4.log）与 NUT_LOCAL_CASH_REWARD_PASS（diamond-model-play.log）。Play 覆盖两国、双余额、广告回调重复保护与跨场景存档。
