# Color Nut Party 录像流程调整

流程参考：20261012061133_rec_.mp4（约 181 秒），以及本次提供的 Withdrawal History 截图。

## 已接入流程

1. 前两关结算领取实际配置金额，随后打开提现目标提示、关卡提现详情、加载提示、账号表单。
2. 关闭表单时，已领取的对应奖励从当前现金余额转入历史记录，保留 Withdraw 入口；同一笔只转入一次。
3. 确认账号后播放三个请求检查步骤，最终确认将本地记录设为 Pending。未接入付款接口，不设置已付款标记，不显示到账成功。
4. 两笔奖励归档后，自动播放评估、激活、五项奖励说明、500 美元横幅、激活完成、记录说明。横幅约 1 秒收集、2 秒结束，无额外 Continue 按钮。
5. 美国地区 500 美元沿用已有配置的绝对余额规则；已有更高余额保留。发奖和动画确认分别持久化，中途重启可以恢复动画但不能重复发奖。原存档已有激活完成标记时直接兼容迁移。
6. 第三关起，完成单根杆获得原配置的现金奖励，并按原触发计数／时间打开 Lucky Reward。Lucky 与关卡结算均提供普通领取和激励广告领取 10 倍；倍率来自当前配置，只有成功的激励广告回调可以发放。
7. 第三关结算保持现金奖励；进入第四关播放钻石奖励预告及入口引导。预告数字本身不发钻石。
8. 关卡完成优先于 Lucky，普通广告失败仍完成已赚取的基础奖励，重复或晚到的回调不再次发奖。
9. 完成杆后、延迟奖励回调前退出时，重启按已保存的完成计数补齐未结算奖励；余额和处理计数一起保存。已完成棋盘恢复同一关结算，不要求重玩；已有结算记录时不会另发一笔。

## 记录与数值来源

- 前两笔金额来自实际结算，不固定写死为 0.40／0.60。日期是本地首次记录／提交时间，旧存档缺失日期保持空白。
- 第三行显示当前现金余额，是提现入口，不伪造一笔已付款记录。
- Lucky 原后台算法没有可用接口；本实现明确复用项目现有的本地现金分档和随机系数，不把录像单次金额 3.32 当固定规则。
- 录像中的他人到账统计不作为实际支付数据生成。
- Level Stats 仍无真实后台统计值，保持既有缺省显示；本次没有虚构人数、尝试次数或平均提现金额。

## 工程边界

- 静态 UI 存入独立 Prefab，点击使用标准 Button 并由代码绑定；参数、文案、路径和时长在 Resources/Configuration 中。
- 没有通过反射调方法，没有添加 Editor 专用核心流程。
- 广告继续经现有 QTGameAdsBridge 调用 SDKAdapter；Assets/SDK 的 84 个文件哈希保持不变。
- 当前项目未实现此前方案文档中的 resource_change 自动观察器。本次流程调整没有声称已完成那套独立打点方案。

## 验证与交付

- `validation/report.json`：主流程、历史记录、真实 UI 点击、长短屏布局、重启与广告回调验收。
- `lucky-validation/report.json`：真实世界杆移动触发奖励、Lucky 领取与通关优先验收。
- `lucky-policy-report.json`：奖励和广告结果策略测试。
- `flow-comparison.html`：录像／截图参考与当前 Unity 运行截图对照。
- 截图采用隔离验收存档；两套 Play 验证退出后都校验原存档恢复。广告回调是验收注入的成功／失败结果，没有实际付款。
- APK 的包名、签名、ZIP 对齐、CRC 和新资源版本另见 build-result.json、apk-resources.json。Unity Play 验收不等同于 Android 真机广告回归。
